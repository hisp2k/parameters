# Калькулятор шнекового транспортёра — Тех-Аэро

Статус: **работающий прототип с несколькими реализованными расчётными
модулями и веб-интерфейсом**, всё ещё НЕ промышленно готовая система —
часть модулей (прочность, реальный подбор привода по каталогу, CAD-связь,
технология с подтверждённым оборудованием) остаются черновыми/непроверенными
по прямому указанию задания: не выдумывать данные, которых нет.

## 1. Что реально создано

Работающая цепочка **ввод (веб-форма или CLI) → проверка → предварительная
компоновка → требования к приводу → технология → сохранение проекта →
предварительный лист согласования (HTML+PDF) → блокировки выпуска**:

```
calculator/
  core/
    parameters.py          — единая модель параметра: значение/единица/источник/статус/автор/дата
    roles.py               — три роли + таблица прав + RoleContext (явное совмещение ролей, раздел 5)
    verification.py        — VerificationRecord: числовой результат+критерий+источник+проверка+актуальность
    questionnaire.py       — минимальный ввод (Экран 1, 4 группы) + validate_questionnaire()
                              + unsupported_requirements() (раздел 1.Г)
    screw_engineering.py   — инженерное ядро: диаметр/шаг/обороты/мощность, требуемая vs
                              достижимая производительность (раздел 1.В), ЧЕРНОВИК
    strength_calculations.py — кручение/изгиб+кручение (3-я теория прочности), сварной шов,
                              болтовая группа — реальные формулы, проверенные вручную
    strength_coverage.py   — реестр охвата прочности по BOM (раздел 10), закрытие требует
                              VerificationRecord, а не просто выбора метода (раздел 1.А)
    drive_selection.py     — требования к приводу всегда считаются; подбор по каталогу — только
                              если каталог подключён (раздел 11), честно НЕ путает stандартный
                              ряд с "подобранным приводом"
    technology.py           — технология по частям/сборкам/маршруту (раздел 7), честная проверка
                              оборудования (раздел 16), два разных способа изготовления спирали
    project.py              — Project: ревизии, отпечаток входных данных, аннулирование при
                              изменении анкеты (раздел 1.Б), TechnicalReview/ReleaseApproval
    release_gate.py         — блокировки выпуска (раздел 20) — проверяет факты, а не флаги
  reference/
    normative_registry.py   — реестр нормативов (раздел 8); часть записей ПРОВЕРЕНА независимым
                              веб-поиском с указанием источника, остальное честно "не проверено"
    equipment_registry.py   — оборудование предприятия (раздел 16), из данных пользователя,
                              verified_by_datasheet=False у всех записей
    drive_catalog.py        — иллюстративный каталог моторов/редукторов + импорт из CSV (раздел 11)
  cad_adapter/
    bridge_transport.py     — РЕАЛЬНЫЙ файловый транспорт до существующего SolidWorks-коннектора
                              (протокол ClaudeBridge/CLAUDE_CALL.ps1, раздел 5) + фейковый транспорт
                              для контрактных тестов
    interface.py            — LocalBridgeCadAdapter: реальные попытки чтения/записи через мост,
                              атомарное rebuild_project_copy(); из ЭТОЙ среды can_read()/can_write()
                              честно возвращают False (нет Windows/PowerShell/SolidWorks)
  documents/
    agreement_sheet.py      — лист согласования: HTML+PDF из ОДНИХ данных, с экранированием
    schematic.py            — предварительная размерная схема (SVG для HTML, примитивы для PDF)
  webapp/                   — веб-интерфейс на русском (раздел 2): forms.py (разбор форм),
                              app.py (Flask-маршруты), templates/, static/ — пользователь НИКОГДА
                              не редактирует JSON проекта напрямую
  tests/                    — pytest, 135 тестов (см. ниже)
  app.py                    — CLI-сценарий и общий расчётный конвейер (create_project/
                              recompute_and_save), которым пользуется и веб-интерфейс
  example_input.json        — пример входных данных для CLI
  requirements.txt
```

## 2. Где находятся файлы

Ветка `claude/screw-conveyor-calculator` в репозитории `SolidWorksCodex`
(ветвлена от `main`, НЕ от `claude/director-parametric-pilot`). Файлы — в
каталоге `calculator/` этой ветки.

## 3. Как запустить

```bash
cd calculator
pip install -r requirements.txt

# CLI-сценарий
python3 app.py                      # встроенный иллюстративный пример
python3 app.py example_input.json   # свои данные (см. формат в этом файле)

# Веб-интерфейс (раздел 2) — открыть http://127.0.0.1:5000/ в браузере
python3 -m webapp.app

# Тесты
python3 -m pytest tests/ -v         # 135 тестов
```

Результат CLI-сценария и веб-интерфейса — один и тот же формат данных в
`calculator/data/`: `<обозначение>.json` (проект), `<обозначение>_list_
soglasovaniya.html`/`.pdf` (лист согласования), `<обозначение>_technology_
draft.json` (черновик технологии). Эта папка не попадает в git
(`.gitignore`) — это выход прогона, не боевые данные.

## 4. Какие проверки выполнены и с каким результатом

135 pytest-тестов, все проходят, в том числе:

- Прямые регрессионные тесты на 5 конкретных дефектов, названных в задании
  (обход блокировки сменой флагов; устаревшие результаты после изменения
  анкеты; требуемая vs достижимая производительность при ограничении
  оборотов — воспроизведён точный пример 5→~1.27 т/ч из задания; потеря
  секции `optional` при загрузке JSON; NaN/Infinity/некорректные типы).
- Контрактные тесты CAD-адаптера на `FakeBridgeTransport`: атомарность
  `rebuild_project_copy()` (сбой копирования или записи параметра не
  проходит дальше и не публикует частичный результат), отклонение
  неотображённых/вне-диапазонных параметров.
- Подбор привода: требования считаются всегда; при подключённом каталоге
  проверки помечены честно, включая то, что физически нельзя проверить без
  CAD (разгон/инерция, нагрузки на выходном валу).
- Технология: разделение машинного времени/времени рабочего/продолжительности,
  честная проверка оборудования (ни одна позиция реестра не
  `verified_by_datasheet=True` — поэтому ВСЕ операции сейчас требуют
  подтверждения, а не только токарная/гибка), два разных обоснованных
  способа изготовления спирали шнека.
- Реестр нормативов: каждая запись со статусом "Проверено..." обязана
  ссылаться на реальный источник; частично проверенные записи (например,
  новая серия ГОСТ Р 2.xxx-2023 для ЕСКД, введённая с 01.03.2024) не
  считаются закрытыми, пока применимость к практике Тех-Аэро не подтверждена.
- Веб-интерфейс: создание/редактирование проекта только через форму;
  явный выбор роли на каждое чувствительное действие без наследования
  (менеджер не может подтвердить допущения инженера; инженер не может
  утвердить выпуск; техническая проверка отклоняется, если проверяющий —
  то же физическое лицо, что и исполнитель); попытка обхода через
  `../` в обозначении проекта отклоняется как 404, а не падает.
- Полный CLI-сценарий и полный цикл веб-формы реально запущены (не только
  описаны) — с реальными файлами на диске, прочитанными обратно для проверки.
- PDF проверен на корректность кириллицы визуально (рендер в PNG и
  постраничный осмотр) — шрифты DejaVu бандлятся в репозитории
  (`calculator/assets/fonts/`), а не берутся из системных путей ОС.

## 5. Что является предварительным (честно, по каждому модулю)

- **Инженерное ядро** (`screw_engineering.py`) — черновик на общеинженерных
  формулах, НЕ проверен инженером Тех-Аэро. Независимый поиск (раздел 8) не
  нашёл действующего норматива именно на расчёт промышленных шнековых
  конвейеров — единственный найденный кандидат (ГОСТ 23976-80) отменён с
  1990 года и в любом случае не покрывал бы это изделие (см.
  `reference/normative_registry.py`).
- **Прочность** (`strength_coverage.py`, `strength_calculations.py`) —
  формулы реализованы и проверены вручную на модельных примерах, но НИ ОДНА
  реальная позиция BOM ещё не проверена (`bom_position` везде
  `"уточнить_по_BOM"` — нет подтверждённой BOM-версии сборки).
- **Привод** (`drive_selection.py`, `drive_catalog.py`) — реальные формулы
  требований; каталог — иллюстративный (`verified_source` явно это
  указывает на каждой записи), реальный подбор появится сразу после
  подключения настоящего каталога поставщика через
  `load_motor_catalog_from_csv()`.
- **CAD** (`cad_adapter/`) — транспорт и адаптер реализованы полностью и
  готовы заработать без правок на рабочей станции с SolidWorks; из ЭТОЙ
  среды выполнения `can_read()`/`can_write()` честно возвращают `False`.
  Разбор ответов `sw_features`/`sw_components`/`sw_properties` использует
  правдоподобные, но НЕПОДТВЕРЖДЁННЫЕ имена ключей JSON — первый живой
  запуск на рабочей станции обязателен для сверки.
- **Технология** (`technology.py`) — нормы времени ориентировочные (см.
  `time_basis` у каждой операции), требуют проверки нормативом времени
  предприятия; токарная обработка и листогибочная операция явно отмечены
  как требующие оборудования, которого нет в реестре предприятия.
- **Реестр нормативов** (`normative_registry.py`) — часть записей
  действительно проверена (см. п.4), остальное — только категории без
  придуманных пунктов/редакций (раздел 8 это прямо запрещает).
- **Оборудование** (`equipment_registry.py`) — характеристики со слов
  пользователя, не из паспортов.
- **Лист согласования** — включает предварительную схему (не CAD-вид);
  масса/центр масс берутся из CAD-адаптера, только когда он реально
  подключён.
- **Веб-интерфейс** — работает и покрыт тестами, но это внутренний
  инструмент (Flask dev-сервер, `debug=True`), не подготовлен к внешнему/
  многопользовательскому промышленному развёртыванию (нет логина —
  проверка роли делается явным выбором на каждое действие, а не сессией
  с паролем).

## 6. Что блокирует следующий инженерный этап

- **Раздел 10 (прочность)** — нет ни одного реального расчёта по
  подтверждённой BOM-позиции — только реестр и проверенные формулы.
- **Раздел 11 (привод)** — нет каталога приводов поставщика.
- **Раздел 12 (CAD)** — из этой среды выполнения нет доступа к SolidWorks
  вообще; первый живой запуск на рабочей станции ещё предстоит.
- **Раздел 14-15 (КД/BOM)** — не начаты.
- **Раздел 18 (себестоимость)** — не начат; действующая ставка
  производственного труда не задана (прежняя 970 руб./ч отменена по
  прямому указанию задания — нигде не используется, см.
  `reference/normative_registry.py::CANCELLED_RATE_WARNING`).
- Инженерное ядро само по себе покрывает только один вид конструкции
  (`валовый_желобчатый`) и не покрывает: толщину витка/корпуса
  (нужен прочностной расчёт — частично покрыт `strength_calculations.py`,
  но не подключён к подбору толщины автоматически), двухвальное
  исполнение, углы наклона >20°, многосекционные сборки.

## 7. Какие минимальные данные нужны от пользователя/Дмитрия Александровича

1. Реальный опросный лист и математическая модель по 25-му транспортёру —
   чтобы сверить/заменить черновичные коэффициенты (ψ, E, ω, A, K).
2. Каталог приводов поставщика (двигатель/редуктор/муфта) — раздел 11.
3. Действующая ставка производственного труда (прежняя 970 руб./ч отменена).
4. Подтверждённая BOM-версия сборки — раздел 10/12/14 упираются именно в это.
5. Доступ к рабочей станции с SolidWorks для первого живого запуска
   CAD-адаптера (`cad_adapter/bridge_transport.py`) — код готов, живая
   интеграция не проверена.
6. Нормативы предприятия (раздел 8) — какие ГОСТ/методики реально
   применяются на Тех-Аэро, с редакциями, для позиций, оставшихся
   "не проверено" в `reference/normative_registry.py`.
